# Вкус у дома (WhatToEat)

Приложение за рецепти, седмично меню и списък за пазаруване. Вече работи изцяло
на база данни (Supabase) вместо на `localStorage` — акаунтите, рецептите и
споделянето между потребители са истински.

Без build стъпка, без framework, без `npm install`. Чист HTML + JS.

---

## Файлове

| Файл | Какво прави |
|---|---|
| `index.html` | Обвивка + всички стилове (непроменени) |

| `js/util.js` | Константи, екраниране, toast, модали |
| `js/db.js` | Supabase клиент + всички заявки към базата + кеш в паметта |
| `js/auth.js` | Регистрация, вход, изход, забравена парола |
| `js/views.js` | Начало, споделени рецепти, приятели, профил/меню/пазаруване |
| `js/recipes.js` | Рецепта детайл, форма, седмично меню |
| `js/app.js` | Навигация, роутинг, стартиране |
| `supabase/schema.sql` | Цялата схема — таблици, RLS, тригери, функции |
| `supabase/migration-shopping-items.sql` | Само за бази, създадени преди ръчните продукти в списъка |

# Настройка на Supabase — стъпка по стъпка

## 1. Създай проект

1. Влез в [supabase.com](https://supabase.com) → **New project**.
2. Име: `whattoeat` (или каквото искаш).
3. Database password: генерирай и **запази го** някъде.
4. Region: избери най-близкия до потребителите (напр. `eu-central-1` за България).
5. Изчакай 1–2 минути да се вдигне проектът.

## 2. Пусни схемата

1. В проекта: лявото меню → **SQL Editor** → **New query**.
2. Отвори `supabase/schema.sql` от този репозитори, копирай **целия** файл и го
   постави в редактора.
3. Натисни **Run** (или `Ctrl+Enter`).
4. Трябва да видиш `Success. No rows returned`.

Това създава:

- таблици `profiles`, `categories`, `recipes`, `week_plan`, `shopping_state`,
  `shopping_items`, `friends`
- Row Level Security на всяка таблица (всеки вижда само своето + публичните рецепти)
- тригер, който при всяка нова регистрация автоматично прави профил,
  7-те стандартни категории и 4-те начални рецепти
- функции `username_available()` и `email_for_username()`

Скриптът може да се пуска повторно — започва с `drop`, така че **изтрива
съществуващите данни**. Не го пускай втори път върху жива база.

> **Ако вече си пускал schema.sql преди добавянето на ръчните продукти** в
> списъка за пазаруване: не пускай целия файл отново (ще изтриеш всичко).
> Вместо това пусни само `supabase/migration-shopping-items.sql` — той само
> добавя новата таблица и нищо не трие.

## 3. Настрой Authentication

**Authentication → Sign In / Providers → Email:**

- `Enable Email provider` — включено.
- `Confirm email` — по твой избор:
  - **изключено** = потребителят влиза веднага след регистрация (по-удобно за
    старт, всеки може да си направи акаунт с фалшив имейл);
  - **включено** = трябва да потвърди имейла си (по-сигурно; приложението
    показва „Провери имейла си за потвърждение“).

**Authentication → URL Configuration:**

- `Site URL`: адресът в продукция, напр. `https://whattoeat.vercel.app`
- `Redirect URLs`: добави и двата реда —
  ```
  https://whattoeat.vercel.app/**
  http://localhost:*/**
  ```

Това е задължително, за да работят линковете за потвърждение и за смяна на парола.

## 4. Вземи ключовете

**Project Settings → API** (или **Data API**):

- `Project URL` → напр. `https://abcdefgh.supabase.co`
- `anon` / `public` key → дълъг низ

Сложи ги в `js/config.js`:

```js
window.SUPABASE_URL = "https://abcdefgh.supabase.co";
window.SUPABASE_ANON_KEY = "eyJhbGciOi...";
```

> `anon` ключът е **публичен по дизайн** — вижда се във всеки браузър. Сигурността
> се пази от RLS политиките в базата, не от скриването на ключа.
> **Никога** не слагай тук `service_role` ключа.

## 5. Тествай локално

```bash
python -m http.server 5500
# отвори http://localhost:5500
```

(Отваряне на `index.html` директно с двоен клик няма да работи — Supabase Auth
изисква `http://`, не `file://`.)

Регистрирай два различни акаунта, направи рецепта публична в единия и провери,
че се вижда в другия под „Рецепти“.

# Деплой във Vercel

1. Push-ни репозиторито в GitHub.
2. Vercel → **Add New → Project** → избери репозиторито.
3. Framework Preset: **Other**. Build Command и Output Directory — остави празни.
4. **Deploy.**

Всеки следващ push към `main` се деплойва автоматично.

След първия деплой се върни в Supabase → **Authentication → URL Configuration**
и сложи истинския Vercel адрес в `Site URL` и `Redirect URLs`.

# Какво се промени спрямо старата версия

**Дизайнът и функционалностите са същите.** Разликите са в поведението, което
преди беше невъзможно:

| Преди | Сега |
|---|---|
| Всички „акаунти“ живееха в един `localStorage` на един браузър | Истински акаунти в базата, работят от всяко устройство |
| Паролите се пазеха в чист текст в браузъра | Supabase Auth (bcrypt, сървърна проверка) |
| „Публичните рецепти“ и приятелите не можеха да видят друг човек | Реално споделяне между потребители |
| Изчистване на браузъра = загубени рецепти | Данните са в базата |

Три неща наложително се промениха:

1. **Вход** — полето приема потребителско име **или** имейл. Supabase Auth работи
   с имейли, затова при потребителско име приложението първо пита базата кой
   имейл стои зад него.
2. **Забравена парола** — вече изпраща истински линк по имейл вместо да сменя
   паролата на място (старото беше отбелязано като „демо без имейл сървър“ и
   позволяваше на всеки, който знае нечий имейл, да превземе акаунта).
3. **ID-та на рецептите** са `uuid` вместо `Date.now()` — старите можеха да се
   застъпят.

## Списък за пазаруване

Списъкът има два вида редове:

1. **Автоматични** — събират се от продуктите на всички рецепти в седмичното
   меню. Еднакви продукти с една и съща мерна единица се сумират. Отметките се
   пазят в `shopping_state`.
2. **Ръчни** — каквото добавиш от реда „Добави свой продукт“ (хляб, кафе,
   тоалетна хартия). Пазят се в `shopping_items` и имат × за изтриване.

Двата вида са в един списък, така че принтирането дава едно цяло. Полето за
количество е по желание — оставиш ли го празно, се записва само името.
„🧹 Изчисти отметнатите“ маха наведнъж всички отметнати **ръчни** продукти;
автоматичните не се трият, защото идват от менюто.

Редът за добавяне и × бутоните не се принтират.

## Бележки по сигурността

- **`email_for_username()`** позволява вход с потребителско име, но заедно с това
  дава начин някой да провери какъв имейл стои зад дадено потребителско име.
  Ако това не ти харесва:
  ```sql
  drop function public.email_for_username(text);
  ```
  и в `js/auth.js` махни блока `if(!login.includes("@")){...}` — тогава входът
  е само с имейл.
- Таблицата `profiles` **няма** колона за имейл — имейлите стоят само в
  `auth.users`, до която клиентът няма достъп.
- Всички текстове от други потребители се екранират преди показване
  (`escHtml` / `escJs` в `js/util.js`), защото публичният феед вече показва
  реално чуждо съдържание.
